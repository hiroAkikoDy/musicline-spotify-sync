## 実装の要点（レビュー追記を反映）
- **`addTrackUris` の `added` から追加済み曲を推測しない**: 追加失敗時は `listPlaylistUris` で
  実際のプレイリスト内容を読み直し、存在する曲だけを `recordTracks` して state 保存してから再スロー
- 成功時も追加後に list を読み直し、実際にプレイリストへ入った曲（＝Spotify側の真実）だけを
  state に記録する（state が失われても再検索が止まる）
- プレイリスト作成直後に `saveState`（中断に強い）・月ごと・失敗時にも保存
- 確認プロンプトは書き込み直前の1回のみ（マッチング自体は読み取りのみ）。`--yes` で省略
- プレイリスト名: `ミュージックライン YYYY-MM`・**非公開**（public: false）。削除系APIは不使用
- 月をまたぐ重複曲は最初の出現月にのみ追加（plan の既存挙動どおり）

## 仕様変更の記録（プレイリストの公開状態・ユーザー決定 2026-10-10）
- 当初の指示書（task_4C）はプレイリストを**非公開**で作成する仕様だったが、実機では**公開**として
  作成された（Spotifyアプリの表示 + GET /playlists/{id} の `public: true` で確認）
- **ユーザーが「公開のままで構わない」と判断**（2026-10-10 承認済み）。以降は公開で運用する
- 調査結果（ユーザー指示の3点）:
  1. **実装は public:false を渡していた**: apply.js → playlist.js のチェーンで `isPublic: false` を
     `body {name, description, public: false}` に変換。ローカルエコーサーバで実リクエストを捕捉し
     `body: {"name":"ミュージックライン 2026-10","description":"","public":false}` +
     `Content-Type: application/json` であることを確認（client.js + playlist.js の実コード経由）
  2. **作成時の API 応答の public の値**: 応答を記録していないため不明（応答はログに出さない設計）
  3. **現在値（GET /playlists/{id}）**: `public: true`
- 結論: クライアントの要求は正しく、Spotify が作成時に `public:false` を反映しなかった
  （サーバー側の挙動）。対応は不要（ユーザー承認済み）
